The five public pages now have distinct Arabic search titles and descriptions, a direct introductory summary, four useful questions and answers per page, and related-page links. ## What changed

| Area | Implementation |
|---|---|
| Search metadata | Central page registry in `src/content/search.ts`; unique title, description, Open Graph and Twitter text for every route |
| Share images | Five JPEGs at 1200×630, about 99–153 KB each, technically cropped from the existing illustrative imagery; generated by `npm run assets:prepare:search` |
| Entity identity | Linked Organization and WebSite JSON-LD, with the supplied Arabic/English company names; approved social profiles and telephone are included only when valid values exist |
| Page context | WebPage, CollectionPage or ContactPage; multi-level BreadcrumbList for inner pages once a public origin exists |
| Service discovery | ItemList of the visible catalogue entries, with working anchors; no unverified provider, rating, office, geographic coverage, accreditation or price claims |
| Answers | FAQPage JSON-LD from the same data as the visible answers; stable question IDs and server-rendered native disclosures |
| Internal links | Related pages link the overview, civil networks, IT networks and contact information using descriptive Arabic labels |
| Freshness | Visible review dates and matching `dateModified`; sitemap `lastModified` uses actual reviewed dates rather than the build time |
| Crawl controls | Public HTTPS origin validation, consistent canonical URLs, explicit preview noindex, robots controls and one registry for all sitemap entries |
| Verification | Optional Google and Bing ownership tokens, emitted only when configured |

JSON-LD is serialized with HTML breakout characters escaped. There is no invented search action or search endpoint. The site remains static and does not collect enquiries through a form.

## Current launch state

The owner confirmed that a domain has **not been bought yet**. `NEXT_PUBLIC_SITE_URL` therefore remains blank. The final local build has:

- `noindex, follow` metadata and `Disallow: /` in robots.txt.
- An empty sitemap, with no placeholder production URLs.
- No canonical, `og:url`, or absolute share-image metadata until the public origin exists.
- Relative JSON-LD identifiers for preview inspection; public URL fields and production breadcrumbs are omitted.

Generated sharing assets are available locally. Their absolute metadata URLs activate after configuration and rebuilding. These controls avoid presenting localhost or an invented company domain as the public website.

## Activate when the real domain is ready

1. Configure `NEXT_PUBLIC_SITE_URL` with the owned public HTTPS origin. Do not include a path, query, credentials or nonstandard port. Blank, invalid, local and IP-address origins do not activate indexing.
2. Set `NEXT_PUBLIC_SITE_INDEXABLE=true` for the public production build. Keep it `false` on public previews even if a canonical origin is configured.
3. Add genuine Google/Bing verification tokens if using HTML-tag verification. Never enter placeholder tokens.
4. Run `npm run seo:check -- --production`, rebuild and deploy. These values are captured during the build; changing only the start-process environment does not update prerendered metadata.
5. Check the deployed canonical tags, social images, robots.txt, sitemap.xml, HTTPS, redirects to the preferred hostname, and HTTP 404 responses. Hosting-level redirects must be configured on the eventual hosting service.
6. Verify domain ownership in Google Search Console and Bing Webmaster Tools, submit `/sitemap.xml`, and inspect the five live URLs. Review subsequent crawling and search performance there.
7. When approved contact/location data is supplied, update `src/config/contact.ts` and review the contact FAQs in `src/content/search.ts`. Approve the proposed services and image-use rights before public launch.

The config checker validates syntax and indexing configuration. It cannot prove domain ownership, DNS, hosting behavior, crawl access through a WAF, indexing or rankings.

## AEO decisions and current guidance

The work focuses on clear answers, distinct service topics, normal crawlable text and links, and factual metadata. Google states that established SEO practices remain relevant to its generative search features and that special AI schema or text files are not required. Its current guide says Google Search ignores `llms.txt`; no such file was added as a ranking tactic. [Google's AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

The FAQs help visitors understand the services and provide consistent machine-readable questions and answers. They do **not** promise Google FAQ rich results: Google retired that display starting 7 May 2026. Schema.org FAQPage remains a vocabulary for describing this visible content. [Google documentation updates](https://developers.google.com/search/updates), [Schema.org FAQPage](https://schema.org/FAQPage)

Production robots allow ordinary crawling with the existing wildcard policy. OpenAI distinguishes OAI-SearchBot for search from GPTBot for model training; this update does not create an additional training-specific policy. Any future crawler/WAF policy must preserve that distinction. [OpenAI crawler documentation](https://developers.openai.com/api/docs/bots)

This is a local implementation and validation of technical readiness. No domain purchase, external deployment, Search Console submission, live indexing, AI citation, ranking result or traffic improvement is claimed.
